# Notes on the atproto Spaces alpha

Findings from reading the `permissioned-data` branch lexicons and the
[Bulletin](https://github.com/bluesky-social/bulletin) reference app, August 2026.
None of this is in the published docs yet, so it is written down here.

Sources: lexicons from `bluesky-social/atproto@permissioned-data` under
`lexicons/com/atproto/{space,simplespace}/`, and Bulletin's `lib/atproto/`.
Packages are published at `0.0.0-spaces-alpha-20260818163953` under the `alpha` tag.

## Can a browser-only client do this? Yes.

This was the open question the plan blocked on. The answer is yes, for our
configuration, on three separate grounds:

1. **`appAccess: open`** on `createSpace` is documented as "any app may access the
   space. **No client attestation required.**" The alternative, `allowList`, evaluates
   an attested `client_id` — that is the one that would force a confidential client.
2. **The DPoP key is generated by the client**, not registered in advance. Bulletin's
   `mintSpaceCredential` calls `JoseKey.generate(["ES256"])` per session — WebCrypto
   territory, fine in a browser.
3. **`@atproto/oauth-client-browser` is published at the spaces-alpha version**, so the
   browser OAuth client is part of the alpha, not left behind by it.

Bulletin is server-side for a reason specific to Bulletin: its boards are gated on
Bluesky follows, so it uses `managingAppPolicy` and must *serve*
`com.atproto.simplespace.checkUserAccess` as its own atproto service, with a DID and
service auth. A member list needs none of that.

## Minting a space credential

Two hops, from Bulletin's `lib/atproto/space-credential.ts`:

1. `com.atproto.space.getDelegationToken` against **the user's own PDS**, over their
   OAuth session, for the target space ref → a delegation token.
2. `POST /xrpc/com.atproto.space.getSpaceCredential` against **the space authority's
   PDS**, with `Authorization: Bearer <delegationToken>` and a DPoP proof over a
   freshly generated ES256 key → the credential.

Thereafter every space request carries `Authorization: DPoP <credential>` plus a
per-request DPoP proof bound to that key (`htm`, `htu`, `credential`).

The authority's PDS is found by resolving the authority DID out of the space ref
(`at://{authorityDid}/space/...`) and reading its service endpoint.

## The two constraints that shape the UI

**Only the space owner can enumerate members.** `simplespace.listMembers` says it
"must be called on the space authority's PDS. Requires OAuth with a covering read
grant; **a space credential is not sufficient**, so members hosted elsewhere cannot
enumerate the list." So membership management is owner-only, and everyone else must
see a UI that never tries to list members. Author names for other people's notes have
to come from the notes themselves, not from the member list.

**`listRepos` is the writer set, not the reader set.** It "enumerates only writers,
never readers", is "what the authority claims from write notifications", and "is not
itself authoritative; a repo's host is the source of truth". So it is the sync
boundary: a member who has never written does not appear, and the `rev` it reports may
lag. Sync therefore treats it as a hint and re-reads each repo.

## Shape of a space

```
at://{authorityDid}/space/{spaceType}/{skey}/{authorDid}/{collection}/{rkey}
```

A space type is declared as a Lexicon def with `"type": "space"` — not a record, not a
query. Bulletin's:

```json
{ "lexicon": 1, "id": "my.bulletin.board",
  "defs": { "main": { "type": "space", "key": "literal:self",
    "name": "Bulletin Board", "collections": ["my.bulletin.post", "..."] } } }
```

`createSpace` takes `{ type, skey?, policy, appAccess }` and anchors the space on the
authenticated user's DID, who becomes the owner. Our call is
`policy: memberListPolicy`, `appAccess: open`.

## API surface actually available

`com.atproto.space`: applyWrites, createRecord, putRecord, deleteRecord, getRecord,
listRecords, getRepo, getLatestCommit, listRepoOps, listRepos, listSpaces, getBlob,
listBlobs, getDelegationToken, getSpaceCredential, registerNotify, unregisterNotify,
notifyWrite, notifySpaceDeleted.

`com.atproto.simplespace`: createSpace, updateSpace, deleteSpace, getSpace,
addMember, removeMember, listMembers, checkUserAccess.

Reads take `{ space, repo, collection?, limit?, cursor?, excludeValues? }`; writes take
`{ space, repo, collection, rkey?, record, validate? }` — the same shape as the public
repo methods with a `space` added.

`registerNotify`/`notifyWrite` push write notifications to a registered HTTPS endpoint.
We do not use them: that needs a public server, and polling on load is sufficient at
family scale. Noted as the upgrade path if the map ever feels stale.

## What is not verified here

Everything above is read from lexicons and reference source, not executed. A live
run needs an account on a spaces-capable PDS — the hosted sandbox is invite-gated at
`bsky.network/account`, and the self-hosted route needs Docker, which this development
container has no daemon for. `scripts/spike.ts` performs the end-to-end check and is
the first thing to run once accounts exist.

## Scopes

Bulletin asks for `include:my.bulletin.permissions` — a `"type": "permission-set"`
lexicon it publishes, which gives a friendlier consent screen. That only works once the
lexicon is resolvable, which means owning the domain the NSID is built from and
publishing the schemas as records. With a placeholder namespace it is not an option.

The raw scope syntax works instead, and needs nothing published:

```
atproto
space?type=xyz.hyperlocal.space&authority=*&skey=self
     &collection=xyz.hyperlocal.note
     &action=read&action=create&action=update&action=delete&manage=create
```

Checked against `@atproto/oauth-scopes` at the spaces-alpha version by round-tripping it
through `ScopePermissions`: it grants read, create, update and delete on the note
collection and `manage=create` for making the space, and correctly refuses
`app.bsky.feed.post`, so it cannot touch anything else in the account.

`authority=*` is the part that matters for a shared space — a member is reading a space
anchored on the *owner's* DID, not their own, and the parameter defaults to `self`.
Space actions worth knowing: `read` is collection-independent and implies `read_self`;
`manage` is separate from `action` and covers creating, updating and deleting the space
itself.

Switching to a permission set later is a scope-string change plus publishing the
lexicons, and the permission set is already written for that:
`lexicons/xyz/hyperlocal/permissions.json`.
